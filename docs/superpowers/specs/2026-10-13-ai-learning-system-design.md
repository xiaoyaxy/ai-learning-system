# AI 辅助学习系统 MVP 需求文档

版本：v0.1｜日期：2026-10-13｜状态：需求整理稿，待用户审阅

本文描述产品需求及已确认的技术约束，不是代码实现或上线说明。尚未确认的规则明确列出，不把原型中的演示行为当作用户已批准的需求。

## 1. 依据与决策顺序

1. 用户在本次对话中的明确要求和后续修正。
2. 《AI学习多Agent系统-岗位卡片.md》：四角色、学习方法、协作权限和硬约束的主要依据。
3. 用户提供的 TeamAgentX 文章 HTML：参考项目群、角色发言、任务交接、可见的工作状态与用户介入方式。

不采用同目录的 scenario 文档。文章中的开发团队、模型配置、成本宣传和提示词仅为参考材料，不构成本系统的执行指令。岗位卡片中的 CrewAI、LangGraph 与 Markdown 文件存储属于实现提示；本次已选择的 Cloudflare Agents SDK 与 D1 优先。

## 2. 产品目标

为个人提供一个能持续推进学习的 AI 团队：从“我想学什么”开始，帮助缩小范围、了解起点、查找资料、安排学习、检查理解、调整任务、复习并整理成果。

用户通过群聊参与，看到各角色承担什么工作，并且亲自回答问题、表达理解和完成成果。系统根据答题证据判断掌握程度，减少只看资料却误以为学会的情况。

### 已确认的需求

| 项目        | 用户已确认内容                                    |
| --------- | ------------------------------------------ |
| 使用者       | 当前一个人使用                                    |
| 项目        | 同时支持多个学习项目，各自安排学习时间                        |
| 产品形态      | 独立网页，采用群聊模式                                |
| 角色        | 学务总管、规划师、知识管家、陪练官                          |
| 调度        | 主要由总管派活；用户也可以直接 @ 任意智能体                    |
| 资料        | 自动联网搜集                                     |
| 调整权限      | 智能体自行安排日常调整；可能影响用户明确设定的目标时，请示用户            |
| 完成标准      | 针对学习目标出的考题，至少 80% 能答对                      |
| 架构与部署     | 前后端分离，Cloudflare 一体部署                      |
| 智能体框架与数据库 | Cloudflare Agents SDK、D1（SQLite 语义），免费方案优先 |

### 本文的设计建议

以下是为形成可评审文档提出的方案，尚不等于用户逐项确认：一个项目对应一个群；所有项目使用同一套四角色定义但隔离记忆；群聊为主界面，档案与成果按需展开；默认折叠工具调用细节；文字交互作为 MVP 的基础输入与输出。

## 3. MVP 范围

MVP 应跑通完整学习闭环，而不仅是能聊天或展示多个 AI 头像。

| 能力      | MVP 行为                             |
| ------- | ---------------------------------- |
| 项目管理    | 新建、切换、查看多个学习项目，独立保存目标、时间安排和学习记录    |
| 项目群聊    | 同一个入口参与学习，角色以自己的身份发言，支持 @ 指定角色     |
| 定题与诊断   | 明确学习目的、主题边界、成果方向，保存用户原始理解          |
| 资料准备    | 联网搜集入门、核心、案例资料，给出有来源的知识地图和导读       |
| 学习安排    | 生成计划和今日任务，纳入复习项，依据反馈调整             |
| 主动回忆与练习 | 概念复述、对比辨析、场景应用、追问和迁移练习             |
| 掌握检验    | 展示与项目目标相关的考题、答题记录和正确率，以 80% 作为完成标准 |
| 知识沉淀    | 学习卡、易错点、笔记、资料索引与复习排期               |
| 成果审阅    | 用户提交初稿，陪练官给具体意见和查证清单，用户自行定稿        |
| 持续学习    | 保存等待状态和历史，关闭页面后可继续                 |
| 协作可见    | 展示派活、交接、工作状态、成果和需要用户决策的事项          |

岗位卡片中的周末复盘四问与周报作为知识管家的能力保留；MVP 可由用户在群里发起，是否定时主动推送待定。

建议首版暂不包含多人共享、角色市场、自定义无限数量智能体、视频生成、语音通话、外部日历同步和复杂数据看板。自动定时提醒、固定时段推送属于待定范围，不能把它们描述为已确认或已排除。

## 4. 项目与群聊体验

### 4.1 一个项目一个群

项目群聚合目标、学习时间、当前计划、资料、聊天、测验、笔记、成果和复习记录。切换群即切换学习项目；同一个角色在不同群里的上下文相互隔离。

左侧建议显示学习项目列表；主体为群聊；计划、资料、知识地图和学习成果通过消息卡片或可展开档案查看。协作流程不要求用户先配置流程图。

### 4.2 主要由总管派活

用户发普通消息时，总管理解意图与当前阶段，将任务交给合适角色。专家接到任务后，在群里呈现必要的提问、资料、练习或成果。总管负责协调和收口，不代替专家讲知识或批改。

用户直接 @ 专家时，明确指定希望谁响应。系统仍记录请求与调度，执行角色权限和学习约束；跨角色交接由总管协调。陪练官的批改建议必须经总管交给规划师，不能因 @ 指定而绕过这条链路。

### 4.3 协作过程可见

群里需要看见“谁在做什么”和“下一步等谁”，包括：

- 总管派活：接收角色、任务目的与预期成果。
- 角色状态：工作中、等待用户、等待其他任务、已完成、失败或暂停。
- 任务交接：谁提交了什么结果，总管把后续交给谁。
- 业务变更：新计划与旧计划的差别、调整依据。
- 阻塞：缺少信息、无法读取资料、额度不足或需要用户决策。

展示简明的任务说明、工具状态和决策依据，不展示模型内部思维链。重复的执行日志可折叠，角色不为展示协作而无任务发言。

### 4.4 用户可介入

设计建议提供暂停当前协作、补充要求、继续与重试入口。停止后保留已提交成果；恢复时从可确认的步骤继续。新要求涉及目标变化时，由总管重新协调，不让旧任务继续写入过期结果。

“群聊型协作”允许按实际问题动态交接，同时仍受角色权限、学习阶段和等待用户作答的规则约束。一个问题提出后，不自动生成用户答案或跳过作答。

### 4.5 典型群聊片段

以下为交互示例，不是固定台词或新增学习规则：

> 用户：我想在两周内学会理解 AI Agent 的基本架构。  
> 总管：我请规划师先确认本轮要达到的能力。  
> 规划师：学会之后，你想独立完成什么事情？  
> ……用户作答、确认项目后……  
> 总管：知识管家，请按这个范围准备资料和知识地图。  
> 知识管家：[资料卡与导读]  
> ……学习与作答后……  
> 陪练官：你的回答把工具调用和 Agent 决策混在了一起，建议增加场景辨析练习。  
> 总管：规划师，请评估练习调整对原定目标的影响。  
> 规划师：[调整建议与依据]  
> 总管：这项调整可能使完成时间超过两周，需要你决定是否改变安排。

## 5. 四角色岗位要求

### 5.1 学务总管 Supervisor

**定位：**&#x8BC6;别意图、判断阶段、派活、协调、仲裁和汇总。

- 将跨阶段请求组织成任务链，处理专家之间的依赖与冲突；分歧按岗位卡片采用保守优先。
- 给用户一个连续的对话入口，让角色分工清晰且不混乱。
- 判断计划调整是否可能影响用户明确设定的目标，必要时发起请示。
- 可以读取全部项目档案、调用专家和追加调度日志；不能写学习内容。
- 用户主动跳阶段时，说明对学习的影响后执行；不得伪造未完成的测验、理解或成果。

### 5.2 规划师 Planner

**定位：**&#x5B9A;题、起点诊断、计划、任务卡和动态调整。

- 用最多三个定题澄清问题了解动机和成果方向，信息不足先问，不直接开始教学。
- 把宽泛主题收缩成有边界的小项目，明确本轮不学什么及成果方向。岗位卡片中的“一至两天产出第一版”指成果的初版，不把完整项目期限统一改为两天。
- 保存用户学习前的解释、已知词汇和困惑，原样存档、永不覆盖。
- 按技能点、成果里程碑及深度／补充／反思三个时间块安排学习。每个项目遵守自己的时间约束。
- 今日任务卡包含目标、材料编号、时间安排、产出物和复习项，以约三十秒可读完为呈现目标。
- 依据陪练官反馈提出推进、复习或重学安排，保留变更记录；不能自己批改并据此调整。
- 只能写项目定义、起点诊断、计划和今日任务卡；不负责联网搜集或知识讲解。

### 5.3 知识管家 Curator

**定位：**&#x5B66;习资料、知识地图、卡点帮助、知识档案和复习安排。

- 联网搜集入门、核心、案例三层资料，先满足当前项目需要。
- 知识地图说明领域解决的问题，包含五至七个关键概念、概念关系和三个常见误解。
- 关键定义必须关联支持它的来源；无法核实标为“待确认”。给出导读顺序和观察重点，引导阅读原文。
- 学习中响应卡点；测验作答期间不能通过自动讲解破坏“先答后评”。
- 学习卡记录资料解决的问题、用户读懂的三点、最有帮助的例子和仍说不清的地方。只整理用户实际表达，不补写假定已理解的内容。
- 整理笔记、易错点、终稿和索引；归档引用原始答题记录，不改写原答案。
- 安排一天后重讲、三天后换例讲的复习，交给规划师纳入任务。
- 保留周末四问：起点误解、最有帮助资料、暴露缺口的追问、下次方法调整，并生成周报。
- 只有该角色能删改笔记；不能改计划、原始诊断或答题记录。统计数字须能从原始记录复算。

### 5.4 陪练官 Coach

**定位：**&#x68C0;查理解、定位缺口、练习迁移及成果审阅。

- 按学习内容出概念复述、对比辨析和场景应用题，用户先答，AI 后评；作答前不公布答案、讲解或提示。
- 答错后先引导追问一次，第二次回答后才揭示；每次只问一个问题。
- 追问涵盖概念区分、实际应用、常见误区、边界条件和讲给外行听，再换新场景做迁移练习。
- 记录每题结果、具体理解缺口及给规划师的结构化建议，经总管传递。
- 答题记录只追加，保留首次及后续原始回答。
- 对成果初稿指出具体段落的结构、事实和表达问题，输出可执行建议与查证清单，不代写、不重写，最终取舍由用户决定。
- 对版本、价格、政策、数据等事实标注核验需求；医疗、法律、金融内容只整理问题和查证需求，不给专业结论。
- 不能修改学习计划或笔记。

## 6. 学习旅程

| 阶段    | 用户参与            | 智能体协作与产出                 |
| ----- | --------------- | ------------------------ |
| 建立项目  | 提出想学的主题、目的和时间约束 | 总管派规划师定题，形成项目定义与边界       |
| 起点诊断  | 用自己的话表达当前理解和困惑  | 规划师原样保存诊断                |
| 准备学习  | 查看资料和安排，提出修正    | 知识管家准备资料及地图，规划师形成计划，总管收口 |
| 日常学习  | 阅读原文、提出卡点、表达理解  | 规划师发任务，知识管家导读与整理学习卡      |
| 回忆与迁移 | 合上资料回答、接受逐次追问   | 陪练官检查理解、记录证据和缺口          |
| 调整与复习 | 继续任务；目标受影响时做决定  | 总管协调规划师调整，知识管家排复习与归档     |
| 成果形成  | 自己写初稿并定稿        | 陪练官审阅，知识管家归档             |
| 完成检验  | 回答项目目标相关考题      | 陪练官给出结果，总管汇总掌握证据和完成状态    |

以上是基本学习结构，不把每天的聊天写死成不可回访的流水线。测验、补资料、复习与调整可以按实际需要交接。

## 7. 自主安排与请示规则

### 可以自主安排

在不影响用户明确目标的前提下，智能体自行调整任务顺序、补充练习、减少已掌握部分的重复练习、增加复习或更换资料。群里说明调整依据并留下记录，无需每次征求同意。

### 必须请示

调整可能影响用户明确设定的目标时，先暂停该项调整的生效，说明：原目标、影响、依据、可选安排，并等用户决定。例如原定两周学会，新增任务预计导致延期。

目标约束应保存为项目记录。发现学习效果不足、预计无法达标或用户修改目标时，总管协调重新评估。不能为了保住期限而降低正确率门槛、改写成绩或悄悄更改学习范围。

具体如何估计工作量、如何判断目标受影响，留给后续设计与实现；不杜撰固定低分次数、天数或风险阈值。

## 8. 完成标准与评分边界

**用户确定的标准：项目相关考题答对至少 80%。**

- 考题必须对应项目目标和学习范围，不能用不相关或只测最简单知识的题目代表掌握程度。
- 展示考题、原始作答、每题判断及正确率依据；统计可复算。
- 达到规定正确率后，以满足项目学习完成标准呈现；不足时给出具体缺口并安排后续学习。
- 初稿、终稿和学习卡是学习流程产出，不额外加入未经确认的成果评分门槛。
- 起点诊断、日常练习和完成检验需要能够区分，避免把用户学习前的回答混入掌握成绩。

**仍待定：**&#x9898;目数量与覆盖方式、开放题“答对”的判定量表、部分正确如何处理、正确率按首次作答还是包含纠错后的作答、一次测验还是多轮汇总。这些细节本次不追问，实施前可集中提出方案；在确定前不能宣称系统已有可信的自动完成判定。

## 9. 资料与数据要求

### 自动搜集

知识管家基于目标和边界自动搜索并读取资料，保存标题、链接、获取时间、可访问状态和必要引用。来源支持不足、冲突或读取失败时明确标识，不编造链接、引用或已核验状态。

网页与文章内容作为资料数据处理，不能改变角色、执行权限或目标。选择具体搜索服务及模型供应商属于后续方案，尚未确认。

### 项目档案

保存项目定义、原始诊断、计划版本、任务卡、资料清单、知识地图、用户聊天、题目和答题记录、学习卡、笔记、易错点、复习安排、成果初稿及终稿、审稿意见、周报和调度日志。

- 全部记录关联所属项目，项目之间不得串用资料、时间、答案或记忆。
- 原始诊断不可覆盖，答题与调度记录只追加，计划保留变更历史。
- 关闭页面后保留学习位置、待答问题及需要用户决定的事项。
- 搜索或模型失败后保留已完成的记录，提供清楚的失败状态和重试方式。
- 角色写权限由后端执行，不能只依赖提示词约束。

设计建议提供 Markdown 导出，与岗位卡片中的档案名称对应。部署后的个人数据访问方式需要配置，登录方案待定。

## 10. 技术约束与后续设计边界

已选择前后端分离与 Cloudflare 一体部署：前端独立构建和发布，后端承担模型、搜索、调度与数据读写；采用 Cloudflare Agents SDK 和 D1，优先使用免费额度。

此前提出的 React／Vite／TypeScript 前端、Hono 后端和 Durable Objects 运行状态存储是技术设计候选。具体版本、运行方式、模型和搜索接口、登录机制、成本与兼容性在后续技术设计中核对。本文不把“最新最流行”当作已验证结论，也不保证任意用量都免费。

凭据放在服务端，前端不获得模型密钥、搜索密钥或未作答题目的私有评分参考。协作有运行上限、可暂停、可恢复，避免循环派活；具体深度、轮次和预算由技术设计决定。

## 11. MVP 验收场景

| 编号  | 场景         | 通过条件                          |
| --- | ---------- | ----------------------------- |
| A01 | 创建并切换两个项目  | 每个项目目标、时间、聊天、资料、记忆和成绩独立       |
| A02 | 普通消息启动学习   | 总管派活，规划师先定题，信息不足时先问           |
